# Future Code 初版与现版对比测试报告

2026年11月11日

本轮测试确认了两项具体改进：处理大量工具输出时，现版准备交给模型的数据更少；工具出错后，现版能更完整地记录结果，并继续后续操作。整体研发效率提高了多少，本轮尚未测出。

测试直接运行两个版本的相关代码，未接入大模型。这样可以单独检查程序改进的效果。共进行了114次正式运行，其中包含重复测试，不代表114项不同的研发任务。

初版为项目首次提交b1f9d186（2026年9月18日）；现版为main分支ac378921（2026年11月10日）。测试未修改两版的生产代码。

## 测出了哪些改进

| 测试内容 | 初版 | 现版 |
| --- | --- | --- |
| 同一批代码审查输出，处理后准备交给模型的数据量 | 121,713字节 | 35,219字节 |
| 输出较少时，同样统计数据量 | 25,689字节 | 25,689字节 |
| 5种人为设置的工具故障，通过预定检查的场景数 | 0/5种 | 5/5种 |
| 正常执行164段已有正确答案的程序 | 164段均通过 | 164段均通过 |
| 执行同一批程序时，人为触发一次返回结果的故障 | 执行33段后退出 | 执行完全部164段 |

每项主要对照均重复4次。程序来自HumanEval数据集，直接使用其标准答案；本轮只检查执行过程，不评模型编程能力。

71.06%的降幅来自第一项测试：相同的审查输出经两个版本处理后，统计准备好的模型输入数据量。完整输出另存为文件，逐份核对后均与原文一致。这个数字不能直接换算成token或费用节省，也不能说明所有任务都能提速。

## 工具出错后，两版有什么不同

先写明通过标准，再人为触发故障。检查三件事：每次操作是否留下成功或失败的记录，已完成的文件操作是否正确，后续能否读取实际结果。每种故障重复4次。

| 人为设置的故障 | 初版表现 | 现版表现 |
| --- | --- | --- |
| 操作尚未返回结果时出错 | 程序退出 | 记录错误，后续读取正常 |
| 文件写完后，返回结果时出错 | 程序退出 | 保留文件和错误记录，后续读取正常 |
| 文件已写完，但没有返回结果 | 后续能读文件，；原操作缺少结果记录 | 补充错误提示，后续读取正常 |
| 整理工具返回结果时出错 | 程序退出 | 保留结果并提示错误，后续读取正常 |
| 执行前检查工具参数时报错 | 调用未正常处理 | 进入正常报错流程，后续读取正常 |

在正常操作和普通工具报错两项对照中，两版均4次通过。初版在“没有返回结果”的场景中仍能继续读取，不能笼统地说初版遇到故障就会停止。人为故障测试也不能用于推算实际任务的故障率。

## 测试方法与结论范围

两版使用同一台机器、同一批输入和同一套检查程序。初版原有的搜索、并行执行和输出保存功能均予保留。统计模型输入前，两边都先应用Bash原有的30,000字符单工具输出上限，避免人为放大初版的数据量。

现版增加了批量输出处理步骤，所测本地处理时间的中位数为2.741毫秒，初版为0.045毫秒。正常执行164段程序，两版分别用时约5.067秒和5.209秒。这些短时测试不足以判断一般任务的耗时变化。

完整智能体评测应让系统实际完成任务，再独立检查结果。SWE-bench用项目测试验收智能体提交的修改，Inspect分别记录执行过程、评分和日志[1][2]。本轮未接入模型，只验证运行机制，尚不能给出完整智能体的基准成绩。

## 下一步怎样证明整体研发效率提高

两版接入同一模型，在相同时间、费用和工具权限下完成同一批新任务，由独立测试判定是否完成。失败、重试、验证和人工介入都计入成本，比较任务完成率、完成时间和实际费用。详细方案见仓库评测方法说明。

考核材料可表述为：已完成Future Code初版与现版的运行机制对比。在所测场景中，现版准备交给模型的数据量减少71.06%，完整输出保持一致；5类工具故障测试均达到预定标准。整体研发效率的提升幅度，还需同模型任务测试确认。
