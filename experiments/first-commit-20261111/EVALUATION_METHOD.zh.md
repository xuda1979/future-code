# Future Code 初版与现版评测方法

本文件说明现有测试能回答什么问题，以及证明整体研发效率还需要做什么。现有实测数据不变。新增的端到端方案尚未执行，不能计入已完成成果。

## 一 本轮属于运行机制测试

本轮直接运行初版和现版的相关生产代码，未接入大模型。外围服务使用相同的测试适配程序。因此，可以检查某项程序改进是否有效，不能据此判断完整智能体完成研发任务的能力。

| 本轮测了什么 | 可以得出的结论 | 不能据此声称 |
| --- | --- | --- |
| 相同工具输出，经两个版本处理后准备交给模型的数据量 | 所测大输出场景的数据量减少71.06%，完整输出已另存并核对 | token、费用或总工期也减少71.06% |
| 5种人为触发的工具故障，每种重复4次 | 现版在这些场景中达到结果记录和后续执行要求 | 实际故障率下降多少，或任何故障都能恢复 |
| 执行HumanEval提供的164段正确程序 | 正常执行以及出现一次指定故障时的流程表现 | 智能体在HumanEval上的自主编程通过率 |

共114次正式运行，包括同一场景的重复测试；不是114项独立研发任务。不能把确定性场景重复4次当成4个独立任务，也不能据此给出面向真实研发任务的统计显著性结论。

## 二 专业评测依据

SWE-bench官方评测把智能体实际生成的代码修改应用到指定版本的项目，再运行项目测试，判断问题是否解决。官方工具还保留逐题的修改、测试输出和评测记录。[1]

Inspect将任务执行、评分和日志分开处理，并支持记录模型用量、错误及多次运行。这些机制便于追查分数来自什么过程，以及失败发生在模型、智能体还是评测环境。[2][3]

本项目采用这些方法中的可复现、独立检查和完整留痕原则，不表示现有脚本已经运行了SWE-bench或Inspect，也不表示获得了官方认证。现有测试还缺少实时模型和完整智能体执行，不能作为标准智能体榜单成绩。

## 三 整体研发效率的正式对照方案

以下是本项目拟采用的方案，不是SWE-bench或Inspect规定的统一样本量。

### 1 固定比较对象

- 初版固定为项目首次提交 `b1f9d186085562947adf682f4c7f65652886ecad`。
- 现版固定为 `ac3789210d0d58d30f1f9b141ca6d842297f7f94`；后续版本另列，不与它混为一组。
- 两版使用同一个实际模型版本、同一模型服务、相同生成参数、相同机器和项目初始状态。保留各版自身的提示词与调度机制，因为它们是被比较系统的一部分；外部任务说明保持一致。
- 每题统一时间、费用、输出、工具调用和外部权限上限。多智能体版本还要统一总模型调用额度，不能靠增加资源形成表面优势。
- 若初版必须修补依赖才能运行，只允许不改变行为的兼容性调整，完整记录修改，并先证明两边可以执行同一个正常任务。做不到时，该项对照不成立。

### 2 预先确定任务，避免挑题

- 编程任务使用SWE-bench等公开基准的固定版本和官方判分程序，明确使用哪个数据集、哪些题目；不把部分题目的成绩写成整个基准成绩。
- 另外加入未公开、未用于调试的真实研发任务，覆盖缺陷修复、功能开发、实验复现等工作。公开基准的潜在训练污染风险与自建任务分别报告。
- 先用一小批独立任务检查整条评测流程，调试题不进入最终统计。正式任务清单、随机抽样规则、预算和通过标准在开跑前确定。
- 正式样本量根据希望检测的提升幅度和试运行的方差确定；资源不足时如实报告探索性结果，不把小样本写成普遍结论。
- 如果根据测试结果改进现版，原测试集只能用于开发判断。最终结论另用预先留出的任务验证，不能反复改代码直到在同一批题上获胜。

### 3 由独立测试判断任务是否完成

- 必须让智能体自己阅读问题、查看项目、执行工具并提交产物，不能向它提供标准答案或固定正确补丁。
- 评分程序独立运行，智能体不能修改测试、参考答案、通过标准或结果文件。
- 编程任务检查目标问题是否解决、原有功能是否回归；研究任务预先写明数据、数值容差、复现实验和产出要求。模型声称“完成”不计成功。
- 容器或隔离环境、项目版本、数据和测试版本均固定。正式实验开始前分别验证正确产物能通过、错误产物不能通过。

### 4 全部计入失败与成本

| 指标 | 统计方法 |
| --- | --- |
| 任务完成率 | 在预定预算内，通过独立检查的任务数除以全部纳入评测的任务数 |
| 固定预算下的产出 | 在相同总时间、模型费用及算力约束下，实际通过检查的任务数 |
| 完成时间 | 从收到任务开始，到独立检查通过为止，包括规划、模型调用、工具执行、重试与验证 |
| 实际费用 | 使用模型服务返回的用量与账单；缺失时记为未测，不用字符数代替计费token |
| 可靠性 | 失败、超时、无响应、错误宣告完成、丢失结果及恢复情况 |
| 人工介入 | 介入次数、原因与耗时；需要人工救援的结果单独列出 |

失败和超时保留在分母中。未完成任务按失败或“在截止时间内未完成”处理；任务还没做完时，不能拿它提前退出的短耗时计算提速倍数。确属基础设施问题的记录也保留，按预先确定的规则区分、补跑，并同时报告原始结果。不能看见结果后临时删掉不利样本。

### 5 成对比较并报告不确定性

每道题都由两个版本分别完成，运行顺序交错或随机安排；多次运行时记录随机种子和实际模型标识。不同任务才是主要统计单位，同一题的重复运行不能当作互相独立的新题。

分别报告完成率差、时间和费用分布，以及按任务汇总的95%置信区间。需要时按项目或任务类别分组，避免把相近任务当成大量独立证据。不能只展示胜出的任务，也不能只比较两个版本恰好都成功的样本而省略总成功率。样本不足或区间不能排除无提升时，结论写为“尚无充分证据”。

### 6 保留可供他人复核的记录

每次运行至少记录：任务编号、两版提交号、模型及参数、原始项目和数据版本、预算、开始结束时间、全部模型和工具调用、实际产物、独立测试输出、用量、异常和人工介入。每次正式运行使用唯一编号，避免误用旧缓存或旧结果。[1][3]

## 四 本轮专业性复核结果

- 已固定真正的首次提交和被测现版，逐项核对生产源码，未用禁用搜索或强制串行等方式削弱初版。
- 大输出测试已纠正为Bash实际声明的30,000字符单工具上限，两边同样应用。早期50,000字符的17次试运行保留但不纳入正式结论。
- 保留了小输出、正常操作及普通工具报错等对照，也报告了现版新增处理步骤的本地耗时。
- 结果依据原始文件和日志复算，并验证了被篡改的计数或文件内容会被检查程序拒绝。
- 未覆盖完整智能体自主解题、实际模型费用和长期项目。HumanEval只用于固定程序的执行测试，不作为自主编程成绩。

因此，本轮数据适合说明具体运行机制改进，不足以证明“整体研发生产力已提高多少倍”。这条限制应与结果一起呈现，而不是藏在附录里。
