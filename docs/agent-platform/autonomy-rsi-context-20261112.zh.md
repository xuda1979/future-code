# 自主运行、上下文管理与自改进修复说明

## 这次解决的问题

| 问题 | 原因 | 修改后的行为 |

| 自改进未推送时，下一轮不能继承上一轮已验证的修改 | 私有工作区总从远端 main 建立，而本地已合并的改进尚未推送 | 从经过构建、测试和合并记录认证的本地主干继续改进；拒绝陌生提交、脏工作区、错误仓库和分叉历史 |

## RSI 如何利用项目经历

前台将目标进入复核、目标受阻、上下文恢复等宿主观测写入有界反馈文件。仅保存项目标识的哈希、事件类别和可选计数，不保存原始目标、错误文本、工具输出或对话。

后台分析最多读取最近 12 条反馈，结合当前源码寻找可重现的问题。反馈只能帮助确定排查方向，不能证明修改正确。候选修改仍须在独立的新工作区中构建，并通过原有离线验收。模型声明目标完成只记作“进入复核”，不记作项目成功。

本地连续改进最多允许 128 个尚未推送、且有验证记录的提交；超过此上限时停止自动扩展，保留已有候选供处理。这是明确的运行边界。

### 启用条件和生效范围

现有默认设置仍为 `enabled=false`、`autoMerge=false`、`autoPush=false`。需要持续生成并在验证后合并本地候选时，可在既有 settings 配置中设置：

```json
{
  "selfImprove": {
    "enabled": true,
    "intervalMinutes": 45,
    "autoMerge": true,
    "autoPush": false,
    "maxConcurrentCycles": 1
  }
}
```

这些设置作用于托管的源码副本。通过验证并合并的源码需要按现有构建、安装和重启流程投入使用，当前运行的二进制不会在执行任务中途被替换。本次修复使源码改进能够累积；它不构成模型权重自训练，也不能据此宣称已经实现无限递归智能提升。

## 上下文与恢复的边界

- 请求本来能放下时，保留稳定的历史前缀。仅在真实压缩时清理重复的宿主续跑提示，保留人工指令、工具调用及其结果。
- 预览替换为证据引用后不能反而增加序列化开销。完整证据继续保存在日志中。
- 旧版本已经记录的模型回复，仅在持久化请求摘要精确匹配时才能重放。目标、系统指令或上下文改变时，仍拒绝复用旧回复。
- 普通会话压缩和强制修复共用自动压缩开关及失败熔断器。关闭自动压缩、用户取消、明确的调用者轮数上限和钩子停止决定继续有效。
- 修复后保留原目标、工具证据和累计任务预算；不会通过重建一个“新任务”来清零消耗。
- 会话记忆读取失败时尝试普通摘要流程；反馈文件异常不应拖住前台任务。反馈读取拒绝符号链接和管道，且设置有界读取。

## 科研任务中的用途

这些机制处理目标、证据、运行状态和工具协议，不在共享运行时中加入量子计算、生物或化学知识。领域资料、工具和实验判据继续由项目配置与外部适配器提供。

长实验仍需使用项目已有的任务拆解、远端作业状态核对、检查点和独立验收。模型请求失败后，应先核对已有作业，避免重复启动实验。上下文修复只能恢复执行条件，不能把模型回答或一条进程退出码当作科研结论。
