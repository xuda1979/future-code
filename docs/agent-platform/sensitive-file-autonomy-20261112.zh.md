# 已授权敏感文件访问不再重复确认

用户已授予当前账户范围内的完整文件访问权限时，Future Code 应直接完成项目所需的读写。文件名属于凭据或配置文件，不应成为再次索要同一授权的理由；用户明确设置的读写限制继续生效。

原来的权限流水线先处理敏感文件检查，再处理完整访问模式。因此即使普通 CLI 已默认使用 `bypassPermissions`，修改 `.future/settings.json`、`.git/config`、`.vscode/settings.json` 或 shell 配置时仍会弹出确认。PreToolUse 钩子的复核路径也存在同样的问题。

本次修复让已有完整访问模式覆盖可自动批准的文件敏感性检查，并在异步检查结束后读取当前权限状态，避免使用已经撤回的授权。它使用真实宿主权限状态；提示文本和模型回复都不能授予权限。完整访问在计划模式中的既有语义保持一致。

同时修复了会掩盖用户限制的顺序问题：原生文件工具同时检查通用 `Read` / `Edit` 规则和实际 `Write` / `NotebookEdit` 等工具的限制；内部目录允许规则与敏感文件提示不能覆盖显式限制。Bash 和 PowerShell 会检查同一命令、重定向及后续子命令中的所有已识别路径，先返回拒绝，再保留必须处理的路径校验或显式询问。原始路径和符号链接目标都参与限制检查。

| 场景 | 修复后的结果 |
| --- | --- |
| 完整访问模式下读写敏感文件或配置文件 | 在当前操作系统账户权限内直接执行 |
| 用户设置 `Read(...)`、`Edit(...)`、`Write(...)` 或 `NotebookEdit(...)` 拒绝规则 | 拒绝相应操作，不让用户重复授权覆盖拒绝规则 |
| 用户主动设置某路径必须询问 | 保留这项显式要求；其他路径的提示不能将其掩盖 |
| 钩子修改了输入中的目标路径 | 按修改后的路径重新检查限制 |
| 异步检查期间从完整访问切换为受限模式 | 以最新状态为准 |
| 路径语法含糊或无法完成必要的结构校验 | 保留真实诊断，不能被完整访问或自动分类器间接批准 |

这里的文件路径检查覆盖工具能够识别的路径，不是任意 shell 程序的操作系统沙箱。操作系统权限、组织管理控制、明确停止指令和项目验收边界均保持原有约束。
