# Customer R&D pilot: verifiable acceptance contract

## Target buyer

Start with expensive ML research, experiment management, HPC or infrastructure engineering workflows. Establish a named economic buyer, a technical operator, and their actual cost of interrupted work.

## Freeze before running

Record: repository/commit; permission to process customer data; frozen acceptance tests and checker implementation; models and API terms; authorized tools; environment/data/resource hashes; trial budget; baseline; candidate; failure/recovery policy; security boundary; invoice sources; and release approval. Production changes, accounts, credential access, irreversible effects and substantial compute require separate explicit authorization.

## Success metrics and safeguards

- Primary: independently accepted objectives divided by aggregate wall-clock hours; failed quality gates never count as success.
- Secondary: all-in cost divided by verified objectives, only when invoice-based model/compute/verification costs are complete. Unknown is not zero.
- Guardrails: no weaker tests, no reduced quality or verified completion, permission/scope adherence, and no unreconciled external effects.
- At least three live matched baseline/candidate pairs, alternating order; freeze model, tasks, tools, budgets and checks; change only a documented operating recipe. Independently run separate comparisons with contemporary commercial agent products.
- Retain failed trials, source hashes, budgets, report hashes and independent reviewer decisions. Treat a single-project observed gain as narrow evidence only.

## Conversion gate

Pilot completion requires customer sign-off on the predeclared outcomes and credible economic benefit after onboarding, support and infrastructure costs. Publish case studies only with explicit customer consent. Do not pool confidential customers' experimental data without authorization.
